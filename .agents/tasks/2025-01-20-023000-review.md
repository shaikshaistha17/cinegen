# Email Templates Implementation

Complete implementation of CineGen's branded email system with six transactional templates, TypeScript generator functions, and test endpoint.

**Watch for:** OTP code rendering breaks in Outlook (confirmed), TypeScript interface lacks validation (confirmed), lib file duplicates HTML content instead of reading from files (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

All six HTML templates exist with proper structure and DEMO watermarks. Each uses table-based layout for email client compatibility and includes mobile-responsive media queries. The CineGen brand is consistently applied across templates through violet/cyan gradients, dark theme backgrounds, and glassmorphism-inspired styling. Footers are complete with support email, social links, address, and unsubscribe options.

The TypeScript implementation in `lib/email-templates.ts` inlines all HTML rather than reading from the templates directory. This creates maintenance burden: changes to HTML templates require duplicate edits in the TypeScript file. The interface has no validation types, and the generator functions don't verify inputs.

The OTP template uses inline-block divs for code display, which renders incorrectly in Outlook's older rendering engine. Outlook strips unsupported CSS and breaks the layout.

The test endpoint at `/api/test-emails` renders all six templates successfully with sample data and provides a polished preview interface with copy/view-text functionality.

## Issues (7)

<summary>Issues (7)</summary>

2. **HTML duplicated in TypeScript** — `lib/email-templates.ts` hardcodes full HTML instead of reading from `emails/` directory. Refactor to read from filesystem and cache.

4. **Avatar initial in div, not table** — `proposal-received.html` uses `{{CREATOR_AVATAR_INITIAL}}` in a `<div>` with inline-block styling instead of table cells, risking layout breaks in Outlook and with multi-byte characters.

6. **Plain-text fallbacks unusable** — `htmlToText()` strips all tags and collapses whitespace. OTP code is buried, password reset links are missing URLs. Write template-specific plain-text versions.

## Template files and structure

All six templates exist in `/emails/` with table-based layout, inline CSS, and DEMO watermarks. Dark theme (#0f0f1a) with glassmorphism cards. Violet/cyan gradients on brand emails, cyan/indigo on creator emails.

Media queries target mobile (`max-width: 600px`), but Gmail and other clients strip `<style>` blocks, so these won't apply there. Desktop layout shows on mobile in those clients.



## Placeholders and replacement

`lib/email-templates.ts` provides `replaceVariables()` helper that regex-replaces `{{WORD}}` patterns.

**Confirmed issue**: `proposal-received.html` uses `{{CREATOR_AVATAR_INITIAL}}` in a `<div>` with inline-block styling. The generator populates it, but the div layout may break if the name is multi-byte. Avatar circles should use table cells, not divs.

## TypeScript implementation

`lib/email-templates.ts` exports `EmailTemplate` interface and five generator functions. The interface has no validation: accepts any string, no branded types for email or URL. `replaceVariables()` doesn't escape HTML entities, so user input with `<`, `>`, `&` creates XSS risk.

**Major architectural issue**: Each generator function hardcodes the full HTML template as a string literal. This duplicates the content from `/emails/`. If a designer updates `welcome-brand.html`, the change doesn't take effect until a developer manually copies it into the TypeScript file. The HTML files are orphaned reference copies. Generator functions should read from filesystem and cache.

## OTP code display and Outlook compatibility

The OTP template uses `display: inline-block` on a `<div>` for the code box. Outlook 2007-2019 doesn't support inline-block and strips the gradient background. The code appears unstyled or in a plain white box. Convert to table-based layout: wrap the code in `<table><tr><td>` with inline styles.

## Plain-text fallbacks

Generator functions return a `text` field, but the content comes from `htmlToText()` which strips all tags and collapses whitespace into a single-line blob. Placeholders remain unreplaced because replacement only happens on HTML.

Accessible users relying on plain-text email or screen readers get degraded experience. The OTP code is buried in paragraph text. The password reset link is in a button, so plain-text just says "Reset Password" with no URL. Write template-specific plain-text versions with proper formatting: OTP code on its own line, password reset with the actual URL, welcome emails with newline-separated steps.

## Test endpoint

`/app/api/test-emails/route.ts` generates all six templates with sample data and returns a preview HTML page with iframe grid.

The route has no authentication or environment check. It's publicly accessible if deployed. SETUP.md warns to remove it before production, but there's no enforcement. A developer could forget and ship it. Wrap in `if (process.env.NODE_ENV === 'development')` or add middleware.

## SETUP.md documentation

The Email Configuration section covers templates, integration examples (Resend, SendGrid, Supabase SMTP), and troubleshooting. The warning to remove `/api/test-emails` is present but easy to miss in a 15-item checklist.
