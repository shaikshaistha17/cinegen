# Change Password Feature: Review Findings Fixed

This iteration addresses the previous review's findings by adding shared password validation, retry logic for database sync, and improved error messages. The change-password API now uses `validatePassword` from a shared utility module (`lib/password-validation.ts`) that both UI and API consume. Database sync failure risk is mitigated with exponential backoff retries (3 attempts). Error messages no longer expose implementation details about dual password storage.

The fix consolidates password validation into a single source of truth with explicit boolean checks (`minLength`, `hasUppercase`, `hasNumber`) that both client and server can reference. The retry loop waits 100ms, 200ms between attempts before giving up, reducing the window where Auth and the users table diverge. If sync ultimately fails, the error message now explains that the Auth password was updated but database sync is incomplete, instructing the user to retry the change.

**Watch for:** Reset-password endpoint still duplicates validation logic **(likely)**, no test coverage for the retry logic failure scenario **(confirmed)**, retry backoff strategy not documented in code comments **(confirmed)**.

**Verdict**: APPROVED

## High-level view

The shared validation utility exports `validatePassword(password: string)` returning `{ valid: boolean; errors: string[]; checks: {...} }`. This eliminates regex and length-check duplication that existed in the previous version. Both the UI (change password page) and API (change-password route) now import and use this function identically.

The retry mechanism wraps the users table update in a for-loop (3 attempts) with exponential backoff delays (100ms × 2^attempt). If all attempts fail, the API returns HTTP 500 with a message telling the user that Auth was updated but database sync failed, and to retry the password change. This is more transparent than the previous generic "Failed to complete password update" message.

The "User not found in database" error (404) changed to "Failed to verify current password" (401). This prevents leaking that password hashes are stored separately from Supabase Auth. The change is subtle but closes an information disclosure gap.

## Shared validation eliminates regex duplication

The new `lib/password-validation.ts` module exports `validatePassword` with a structured return type:

```typescript
export interface PasswordValidation {
  valid: boolean;
  errors: string[];
  checks: {
    minLength: boolean;
    hasUppercase: boolean;
    hasNumber: boolean;
  };
}
```

The UI uses `validation.checks.minLength` to toggle checkmark icons. The API uses `validation.valid` and `validation.errors[0]` to return a 400 error if requirements aren't met. Before this change, the UI had `const hasMinLength = newPassword.length >= 8` and the API had `if (newPassword.length < 8)` — identical logic, different locations. Now both reference the same function.

The regex patterns (`/[A-Z]/` for uppercase, `/\d/` for numbers) are centralized. If requirements change (e.g., add special character check), one edit to `validatePassword` updates both client and server behavior.

## Retry logic reduces dual-storage inconsistency risk

The API updates Supabase Auth first, then the users table. If the table update fails, Auth has the new password but the table still has the old hash. The previous version returned an error immediately on first table update failure. This version retries 3 times with exponential backoff:

```typescript
for (let attempt = 0; attempt < 3; attempt++) {
  const { error: tableError } = await supabase
    .from('users')
    .update({ password_hash: newPasswordHash, updated_at: ... })
    .eq('id', user.id);

  if (!tableError) {
    tableUpdateSuccess = true;
    break;
  }
  
  lastError = tableError;
  if (attempt < 2) {
    await new Promise(resolve => setTimeout(resolve, Math.pow(2, attempt) * 100));
  }
}
```

The backoff delays are 100ms (after attempt 0) and 200ms (after attempt 1). This is short enough to keep the API responsive (max ~300ms added latency) but long enough to ride out brief network hiccups or database lock contention.

If all 3 attempts fail, the error message is explicit: "Password updated in authentication system but database sync failed. Please try changing your password again to complete the update." This tells the user: (1) their new password works for login (Auth is authoritative), (2) they should retry the change to finish syncing the table.

The retry strategy doesn't eliminate the risk entirely (a persistent database outage still causes divergence), but it reduces the failure surface from "any transient error" to "error lasting >300ms across 3 attempts."

No compensating rollback exists: if table sync fails permanently, the Auth password isn't reverted. Supabase doesn't expose a transactional API that spans Auth and table writes. The current approach prioritizes Auth (login works) over table consistency (password verification for future changes). An alternative design would be to check the table hash before login and re-sync if stale, but that adds complexity to the login path.

## Error message change prevents info disclosure

The old error path returned 404 with "User not found in database" when the users table query failed. This reveals two things: (1) password hashes are stored in a separate database table, (2) the table lookup failed (user might not exist, or query permissions are wrong, or table is unreachable).

The new error returns 401 with "Failed to verify current password". An attacker can't distinguish "user doesn't exist in table" from "wrong current password." The 401 status is semantically correct: the request lacks valid authentication credentials (the current password is part of the auth check).

This is a minor hardening fix. The dual-storage architecture is visible elsewhere (the password_hash column is referenced in other API routes), but each information leak closure makes enumeration attacks slightly harder.





## Reset-password endpoint not updated

The `/api/auth/reset-password` route still has inline validation:

```typescript
if (!password || password.length < 8) {
  return NextResponse.json({ error: 'Password must be at least 8 characters' }, { status: 400 });
}

const hasUppercase = /[A-Z]/.test(password);
const hasNumber = /\d/.test(password);

if (!hasUppercase || !hasNumber) {
  return NextResponse.json({ error: 'Password must contain at least 1 uppercase letter and 1 number' }, { status: 400 });
}
```

This is pre-existing code (not part of the change-password feature), but it creates a consistency gap. If password requirements change, `validatePassword` and this route could diverge. The reset-password route should import `validatePassword` to match the change-password route.

Additionally, the reset-password route doesn't have retry logic for the users table update. If the table update fails there, the user sees "Failed to complete password reset. Please try again." but the Auth password is already updated (same inconsistency risk as change-password had before the retry fix).

## No test coverage for retry logic

The build passes (`npm run build` completes with exit code 0, no type errors), but there are no automated tests for the retry behavior. Critical scenarios not tested:

- Table update fails on attempt 1, succeeds on attempt 2 → should return 200 with success message
- Table update fails 3 times → should return 500 with "database sync failed" message
- Backoff timing is correct (100ms, 200ms delays)
- Auth update succeeds but table update fails 3 times → user can log in with new password, but next password change fails to verify current password

Without tests, future refactoring could break the retry logic or change the backoff timing without catching the regression.

## Build succeeds with no type errors

TypeScript compilation succeeds with no errors. The Google OAuth warning ("@supabase/ssr: createBrowserClient in non-browser runtimes...") is pre-existing and unrelated to this change.
