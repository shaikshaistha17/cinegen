# Creator Services Marketplace

The Creator Services feature extends Cinegen beyond brief-based project matching into a services marketplace where creators can list pre-packaged offerings and brands can browse and book them directly. The implementation spans database schema with RLS policies, three API routes with auth checks, a custom React hook with real-time subscriptions, a creator management dashboard, brand-facing browse and detail pages, and integration points across navigation and homepage.

**Summary**: The feature is functionally complete across all three components (FEAT-001 database/API, FEAT-002 creator UI, FEAT-003 brand UI). Database schema is correct, RLS policies enforce ownership boundaries, API routes validate auth and creator status, TypeScript types are properly defined, the creator dashboard provides full CRUD operations with form validation and real-time updates, brand pages support search/filters/sort, service detail pages include creator profile cards, navigation includes Services link, creator dashboard has Manage My Services card, and homepage displays featured services. Build passes, glassmorphism aesthetic is consistent, responsive layouts are implemented. No critical or major issues found during static review.

**Watch for**: Missing RLS table enablement (confirmed), client-side only form validation (likely), no URL validation for portfolio items (likely).

**Verdict**: APPROVED

## High-level view

The database schema follows existing Cinegen patterns: creator_services table with foreign key to creator_profiles, snake_case columns, check constraint on price_range enum, indexes on query columns, auto-update trigger for updated_at. RLS policies are comprehensive: public reads active services only, creators have full CRUD on their own services, ownership verified via creator_profiles.user_id = auth.uid() subquery. However, the RLS table enablement command is present in rls-policies.sql but not in the initial schema file, which could cause RLS to be skipped if migrations run in the wrong order.

API routes follow Next.js 14 App Router patterns with proper separation: collection endpoint at /api/services (POST for create with creator check, GET for list with filters), individual endpoints at /api/services/[id] (GET public, PATCH/DELETE with ownership check). Auth uses createClient() from lib/supabase for request-scoped sessions. All routes map snake_case to camelCase in responses, support query filters (creatorId, skills array, priceRange, deliveryTime, search via ilike, isActive default true), and return proper HTTP status codes (201 created, 401 unauthorized, 403 forbidden, 404 not found, 500 error).

Creator dashboard at /dashboard/creator/services provides full CRUD: inline form with character counters for title (100 char) and description (500 char), multi-select skills from predefined list, price range dropdown, delivery time dropdown, optional portfolio items (max 3 url+title pairs). Services display in responsive grid with glassmorphism cards, each showing title, truncated description, skills pills (max 4 visible + overflow), gradient price badge, delivery time, Radix UI Switch for active/inactive toggle, Edit and Delete buttons. Form validation is client-side only with error messages below each field. Real-time updates via Supabase subscriptions refresh the list when creator_services table changes. Toast notifications (sonner) for all CRUD operations. Page redirects to /login if no session, and to /dashboard if user is not a creator.

Brand-facing browse page at /services implements client-side filtering: search box (searches title, description, skills, creator name), collapsible filters sidebar with checkboxes for skills (10 options), price ranges (5 options), delivery times (5 options), and sort dropdown (newest, price low/high). Active filters display as chips above the grid with X remove buttons. Service cards show creator avatar+name in header, service title and truncated description, skills pills, gradient price badge, delivery time, and View Details button. Grid is responsive (1/2/3 columns). Empty state when no results. Framer Motion stagger animations on card mount.

Service detail page at /services/[id] uses 2-column layout: left 2/3 shows service details (breadcrumb navigation, gradient title, About This Service section with full description, Skills & Expertise section with all skills as pills, Price Range and Delivery Time cards, Portfolio Samples section with external links if provided), right 1/3 shows sticky creator profile card (fetched separately from /api/creators/[id], includes avatar with gradient background using initial, name and handle, verification badge based on role, bio truncated to 3 lines, stats for rating and projects, hourly rate, View Full Profile link to /creators/[creatorId], Contact Creator button that prompts login if not authenticated, Book Service CTA button). Dynamic price badge color based on range (amber for $10k+, violet for $5k-$10k, cyan otherwise). Responsive: stacks vertically on mobile.

Navigation integration: Navbar.tsx adds Services link with Briefcase icon between Discover and Briefs, active state shows gradient underline with layoutId animation, link appears in both desktop nav and mobile menu. Dashboard.tsx adds Manage My Services card in CreatorDashboard section after Matching Briefs, styled as glassmorphism action card with cyan gradient background, Briefcase icon, description "Post and manage your service offerings", links to /dashboard/creator/services, only visible to creators (role check). Homepage app/page.tsx adds CreatorServicesSection after hero: gradient heading "Creator Services Marketplace", description, fetches 2 featured services from /api/services?isActive=true&limit=2, displays mini service cards in 2-column grid, Browse All Services button links to /services, section hidden if loading or no services.

<summary>Details</summary>

## RLS enablement sequencing gap

The RLS enablement command (ALTER TABLE creator_services ENABLE ROW LEVEL SECURITY) appears in rls-policies.sql but not in creator_services.sql. If the schema file runs but the policies file does not (partial migration, error in policies file, manual schema application), the table exists but RLS is not enabled, allowing unrestricted access. The 5 policies are defined correctly (public reads active services, creators have CRUD on own services via creator_profiles.user_id = auth.uid() subquery), but they won't enforce if RLS isn't enabled. Move the ALTER TABLE command into creator_services.sql immediately after CREATE TABLE so RLS is enabled atomically with table creation.

## Server-side validation gap

POST /api/services accepts body.portfolioItems as-is with no validation. Malformed URLs or incorrect structure get stored directly. The route also doesn't validate title/description length, skills array non-empty, or priceRange enum match. Client-side validation can be bypassed via direct API calls. Database schema enforces NOT NULL on required fields and CHECK constraint on price_range, catching some invalid data, but exceeding character limits or malformed portfolioItems would be accepted.

PATCH and DELETE routes correctly verify ownership: fetch service with creator.user_id join, check creator.user_id === user.id, return 403 if mismatch. GET routes are public (no auth), map snake_case to camelCase, join creator_profiles and users for creator details. Filters work correctly: creatorId, skills (contains array), priceRange, deliveryTime, search (ilike on title/description), isActive (defaults true).

## Client-side only validation

Service form validates title (required, <= 100 chars), description (required, <= 500 chars), skills (non-empty array), priceRange and deliveryTime (required), displaying error messages below each field. Character counters show remaining length. Portfolio items (max 3) accept url and title as free text with no URL format check. Invalid URLs (missing protocol, typos, localhost) would be stored and break as external links on the detail page. Form has Save and Cancel buttons, showing toast notifications on CRUD operations.

Form is bypassed if API is called directly. Database schema enforces NOT NULL on required fields and CHECK constraint on price_range, catching some invalid submissions, but character length and portfolio URL format are not validated server-side.

Real-time updates work correctly: useServices subscribes to "services_changes" Supabase channel, listening for postgres_changes on creator_services table, refreshing the list on INSERT/UPDATE/DELETE.

## Brand discovery and filters

Browse page at /services uses useServices() to fetch all active services, then applies client-side filtering via useMemo: search checks title/description/skills/creatorName (case-insensitive), skills filter matches any overlapping skill, priceRanges and deliveryTimes filter exact matches, sort orders by price range low/high or newest (default). Filters sidebar has checkboxes for skills (10 options), price ranges (5), delivery times (5), and sort dropdown. Active filters display as removable chips above the grid.

Service cards show creator avatar+name header, service title, truncated description (line-clamp-2), skills pills (max 4 + overflow count), gradient price badge (color by range: amber $10k+, violet $5k-$10k, cyan otherwise), delivery time with icon, View Details button. Grid is responsive (1/2/3 columns). Empty state when no results.

Detail page fetches service from /api/services/[id] and creator from /api/creators/[id]. 2-column layout: left shows breadcrumb, gradient title, About This Service (full description with whitespace-pre-line), Skills & Expertise (all skills as pills), Price Range and Delivery Time cards, Portfolio Samples (external links if provided). Right shows sticky creator profile card: avatar (gradient circle with initial), name/handle, verification badge, bio (line-clamp-3), stats (rating, projects), hourly rate, View Full Profile link, Contact Creator button (prompts login if not authenticated), Book Service CTA (no action). Stacks vertically on mobile.
